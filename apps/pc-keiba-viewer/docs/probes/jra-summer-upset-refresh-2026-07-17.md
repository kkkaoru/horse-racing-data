### 2.1 Classification methodology

Neon `race_finish_position_model_predictions` (read-only attach + `SET default_transaction_read_only=on` safety pragma) joined to local-PG `jvd_se`/`jvd_ra` actuals on `(keibajo_code, kaisai_tsukihi, race_bango, ketto_toroku_bango)`, placeholder-guarded. Discovery query across all of 2026 found 26 distinct (model_version, venue) combinations; after excluding known backfill/reconstruction batches (`iter14-jra-cb-pacestyle-course-v8`, legacy v5/v6/v7, other model families), a **row-level** `days_before_race>=0` filter on `prediction_generated_at` (not just a model_version/day-level filter, since backfill and same-day rows were found mixed **within** the same model_version/venue/day cell) narrowed the population to genuine daily-incremental rows: **exactly 2 race days (0711, 0712) across 3 venues, 47 races**. Sapporo: confirmed zero rows and zero real races, consistent with §1. All of 2026 outside these 2 days is either complete blackout or excluded-batch — this is a symptom of the FP serving blackout tracked in `project_fp_serving_blackout_2026_07_09` plus the fact that only one JRA weekend has occurred since the 07-11 CF-only-serving fix.

### 2.2 Why this null result is expected, not a failure of the method

Both the small-n framing above and this campaign's own repeated lesson (a 956-cell Bonferroni sweep found 0/18 nominal hits survive correction) predict exactly this outcome from a 47-race window. Taken at face value, §2.1 alone would already justify "no candidate found here, sample too thin, revisit once more genuine live-serve days accumulate."

### 2.3 Important correction, discovered after §2.1 was built: the analyzed window is not just thin, it is compromised

A concurrent teammate's independent audit — `apps/pc-keiba-viewer/docs/probes/jra-serving-audit-jun-jul-2026-07-17.md`, also dated today — examined the exact same 0711/0712 window from a different angle (serving-pipeline health, not upset-pattern mining) and found that **the 72 scheduled races on these 2 days are, almost entirely, not genuine per-race Cloudflare Container output**. Their finding: predictions in this window show top1≈8.3% against a market favorite baseline of 32.4% and the documented healthy baseline (44.71%/31.78% FULL/DEGRADED), with within-race score standard deviation collapsed to roughly 1/11 of healthy — a signature of scoring on degenerate/default-filled features rather than genuine inputs. They trace this to a single write event (2026-07-12 14:51–14:52 JST, 36 races processed in 23 seconds — a batch-script cadence, not the ~27.5-min/race Container pipeline the system is documented to use) coinciding with a same-day `finish-position-cron`/`finish-position-predict-container` refactor. A separate, genuinely healthy prediction set does exist in this window (21 races, the now-disabled 07-11 Mac-local-batch-fallback incident, top1=42.86%) but it was written under the wrong (default, non-routed) model version and is permanently shadowed from the viewer by the very priority-0 routing logic that exists to prevent a _different_, earlier incident — so it was never user-visible and, being the disabled fallback path, isn't a legitimate reference either.

**This means §2.1's classification counts and attribute-mining are, in significant part, an analysis of a broken batch script's near-random output, not genuine model behavior.** This should be read as a _stronger_, not weaker, version of the "no candidate found" conclusion — there is currently no way to distinguish genuine model miss-patterns from serving-defect noise in this window at all, so no behavioral inference (running style, waku, distance, etc.) should be drawn from §2.1 regardless of sample size. In hindsight, §2.1's own numbers are consistent with this: only 9/47 (19.1%) baseline-correct and only 1/47 clean model-beats-market both read as suspiciously low next to this system's typical ~33-40% top1 rates, which — now — is not a coincidence.

The audit doc's own recommendation is the right one to defer to here: fix Defect A's root cause first, confirm healthy score variance (stddev ≳0.7–1.5, referencing the one known-healthy cluster) on the next genuine JRA racing day (2026-07-18, tomorrow, per that doc), and only then treat 2026-07 production-vs-actual as a usable mining population. **This task's item 2 should be re-run after that**, not before — re-running it sooner would only re-analyze the same compromised window this doc already covers.
