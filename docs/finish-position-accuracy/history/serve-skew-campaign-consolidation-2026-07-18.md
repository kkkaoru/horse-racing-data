## ★ Resolution and closure update (2026-07-19): market-feature skew, without an adopted accuracy change

After this doc's original writing, the RS served-vs-WF gap mechanism (left "unresolved" in the Flagship section below) was **resolved**, and the SAME mechanism was found to drive the FP served-vs-WF gaps in NAR and Ban-ei. The unifying root cause is **market-feature look-ahead**: features derived from `tansho_odds` / `tansho_ninkijun` (and, for RS, `track_condition_normalized`) are built from the race's FINAL / post-close values at train/WF time, but at serve time collapse to a stale / hardcoded-median / NULL fallback — so the model is evaluated (in WF) on information it cannot have in production, and runs effectively market-ablated at serve.

- **JRA RS (task #75, RESOLVED):** NULL-at-serve ablation of `odds_score` / `popularity_score` / `track_condition_normalized` drops WF top1 by **-8.93pp** (2026; -9.05pp on 2024-25) — the entire served-vs-WF gap. The apparent conflict with the 07-11 result is resolved: 07-11 compared an already-nulled serving regime with native serving, whereas this ablation compares populated offline features with nulled serving features. This supersedes the "Remaining candidates" (live-serving-path, calibration, artifact drift) listed in the Flagship section: the mechanism is market-feature serve-NULL, not matview divergence (which stays correctly REJECTED) and not calibration. **Retraining without market features is conclusively dead:** RS v1 already lost **-3.40pp** (UB95 -2.96; 18/19 cells) to prod-v3. A live-odds RS path is only an unevaluated post-campaign candidate; it was not adopted.
- **Calibration hypothesis — REVERTED (tasks #65/#67):** the OvR-isotonic calibrator initially looked like an ADOPT (+2.52pp pooled, LB95 +1.67) but was **reverted, self-caught as a regime-mismatch artifact** — measured on the wrong regime; on the correct regime it would have REGRESSED real serving by **-4.26pp**. Calibration is not the gap.
- **NAR FP (task #69) & Ban-ei FP (task #70), ~16pp gaps each:** the model-side mechanism is the same — `finish_position_features_duckdb.py` builds `odds_score` / `popularity_score` from post-race FINAL odds, while genuine pre-race serving can consume stale/invalid odds and fall back toward hardcoded medians. inv-2026-nar's NaN-ablation reproduced the NAR symptom: WF top1 0.4627 → 0.25-0.28, bracketing served ~0.30. The later matched-lead producer audit **refuted** the claim that upstream category support is missing: the producer is category-neutral, NAR/Ban-ei are intentionally sale-gated, and 2026-07-18 matched-TTP histories plus D1 showed populated NAR/Ban-ei coverage. The remaining problem is pre-race odds freshness/validity at the prediction consumer, not absent NAR/Ban-ei producer support.

## Flagship: RS train/serve matview divergence (task #48)

**Root cause (iron-clad, direction confirmed):** `running-style-feature-sql.ts` (TRAIN, Postgres) builds its entire historical lookback (`rec` CTE) from `race_entry_corner_features` — a derived/pre-materialised table. `running-style-feature-ctes.ts` / `running-style-sql.ts` (SERVE, R2 SQL/Iceberg) builds the equivalent history directly from raw `jvd_se`/`jvd_ra`/`nvd_se`/`nvd_ra`. `race_entry_corner_features`'s only reliable historical writer for years was `generate-win5-overlay.ts`'s side effect — confirmed via launchd audit to have **never run automatically** (manual/ad-hoc invocation only) — and a dedicated replacement refresher (`corner-features-refresh.ts`, created 07-12) had 3 independent bugs that silently failed every write against real Neon until fixed 07-17 (`docs/probes/corner-features-settlement-backfill-heal-2026-07-17.md` in `apps/pc-keiba-viewer/`).

**Measured impact:**

| Metric                                                                                | Value                                                                                                   |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| RS features diverging train vs serve (inv-jra-rs live diff, real races)               | 937/1764 = **53.1%**                                                                                    |
| Rows missing from `race_entry_corner_features` (worst months)                         | **15.74%**                                                                                              |
| Corner-column NULL rate (worst months, summer)                                        | **10.05%**                                                                                              |
| Estimated serving accuracy loss                                                       | **4-10pp**                                                                                              |
| 2026 gap-day rate vs 2016-2025 historical baseline (inv-bug quantification, local PG) | **~7-8x** (13 degraded/gap day-source combos in 2026 through mid-July vs ~1.5/year/source historically) |

**Mechanism:** if a horse's recent-past race lands on a gap-day, TRAIN's history join (`where h.finish_position is not null`) silently drops that race entirely, shifting `recent_rank` so every recent_rank<=5-dependent feature (career stats, corner-norm averages, `weight_avg_5`, `days_since_last_race`) moves together for that horse. The elevated 2026 gap rate concentrates in exactly the months that matter for "recent 5 races" of a horse racing today, which is why the divergence rate is so high despite the historical baseline gap rate being small (~0.4%/year).

**Fix (implemented, inv-feat-rs):** `rec` in `running-style-feature-sql.ts` (TRAIN, Postgres) now reads `jvd_se`+`jvd_ra` / `nvd_se`+`nvd_ra` directly instead of `race_entry_corner_features`, matching SERVE's `normalisedRecSelect` column-for-column (new `SAFE_NUMERIC_EXPR`/`SAFE_SCALED_EXPR`/`SAFE_FRACTION_EXPR` helpers reproduce R2-SQL's `try_cast(nullif(...))` semantics in Postgres, since Postgres has no `try_cast`). Also fixes a smaller, independently-found bug in the same pass: `SAFE_BATAIJU_EXPR` was missing a `nullif(bataiju,'000')` guard, silently casting the "weight not measured" placeholder to a literal 0kg (0.39% of `jvd_se` rows). Verified bit-for-bit against inv-jra-rs's original live-diff tuple (`ketto_toroku_bango=2023107147`): querying raw `jvd_se.time_sa` for this horse's history through the new expression logic reproduces SERVE's exact reported values (`speed_index_best_5=0`, `speed_index_avg_5=1.12`) to the last decimal. tsc/oxlint/full test suite clean (72/72 in `running-style-feature-sql.test.ts`, 7 snapshot assertions re-pinned to the new SQL body), coverage unchanged (≥95% all 4 metrics). Uncommitted — queued for task #45's post-campaign hygiene batch (see below), not landed on the incident branch. This also incidentally fixes a smaller, independently-found parity issue: `race_entry_corner_features`'s build script (`build-corner-feature-table.ts`) drops rows outright when `umaban`/`kyori`/`shusso_tosu` fail a strict numeric regex, whereas SERVE's raw-table read keeps those rows with NULL fields via null-safe casts — same root fix (read raw, stop depending on the matview) covers both.

**Status: root-cause bugs confirmed and fixed, but this is _not_ the explanation for the served-vs-WF accuracy gap.** A decisive test (below) shows the fix doesn't move the needle in the direction/magnitude the flagship hypothesis predicted. Demoted from "campaign's single largest lever" to "real correctness fix, queued as data hygiene" — see below for the full reasoning and what's still open.

### Three mechanism hypotheses tested and rejected

Three hypotheses about _why_ matview divergence would explain the reported 40-42% served vs 45% walk-forward (WF) accuracy gap were built and tested this cycle. **All three were rejected**, on the SAME underlying champion model (`jra-running-style-lgbm-prod-v3`, no retrain, so this isolates the feature-input question cleanly from anything model-related):

| #   | Hypothesis                                                                                                                                              | Test                                                                                                                                                                                                                        | Result                                                                                                                                                                                                                                                                                                                                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Fixing the matview bugs and rebuilding training data recovers WF-level accuracy                                                                         | inv-jra-rs's recovery test (retrain-style, before session limit)                                                                                                                                                            | **REJECTED** — matview bugs are real (confirmed independently) but the recovery test did not close the gap                                                                                                                                                                                                                                                                                           |
| 2   | Raw features reproduce served's lower number (~40-42%); matview features reproduce WF's higher number (~45%)                                            | inv-feat-rs: shadow-scored the existing champion on the SAME JRA 2026-06-01–07-12 held-out window, once built via raw (`jvd_se`/`jvd_ra`, the fix) and once via matview (`race_entry_corner_features`, current train logic) | **REJECTED** — raw scored 46.73% (408 races, 2626 labeled rows), matview scored 48.41% (260 races, 849 labeled rows). Both land _at or above_ WF's 45%; neither reproduces served's 40-42%                                                                                                                                                                                                           |
| 3   | Matview's severe row/label coverage loss for recent dates biases its own accuracy number upward, and an unbiased sample would land near served's 40-42% | inv-feat-rs: same test as #2 — matview kept only 63.7% of races and just 24.5% of rows had a usable label (vs raw's 47.9%), a much smaller and potentially non-representative sample                                        | **REJECTED** — the smaller matview sample scored _higher_ (48.41%), not lower, than the larger raw sample (46.73%) — opposite of what this hypothesis predicts. On the 771 rows present in both builds, predicted-class agreement was 84.3% and target-label agreement was 100% (label computation is stable across builds; the only difference is row coverage, and it doesn't manufacture the gap) |

**The gap itself is real** (not a measurement artifact) — inv-jra-rs's population-controlled test (matching served predictions against WF predictions for the SAME horses/races) found only **57.46%** predicted-class agreement, far below same-model expectations. Notably this is much _lower_ than the 84.3% raw-vs-matview agreement measured in hypothesis #2/#3 above — the true production serving path is more inconsistent with WF than a Postgres reconstruction of "raw" features can explain, reinforcing that the mechanism lives somewhere in the live serving path itself, not in the train-vs-serve SQL dialect divergence. A population confound was also found in the process: WF's evaluation drops ~5 gap-dates for missing ground truth that served's population includes — a real methodological difference between how the two numbers get computed, separate from any causal mechanism, that should be controlled for in future comparisons.

**Remaining candidates for the real mechanism** — **[SUPERSEDED 2026-07-19: the gap mechanism was resolved as market-feature look-ahead — see "Resolution update" at the top. The candidates below are retained for the record.]** (as considered when this section was written, unresolved at the time):

- Live-serving-path reproduction: fetch features through the _actual_ production R2/Iceberg catalog path (not a Postgres reconstruction of the same logic) for the same held-out races, and see if that alone reproduces 40-42%. This is the most direct remaining test and hasn't been done yet.
- Calibration: `calibrators.json` may be applied at serve time but not in the WF/shadow-score path (or vice versa) — hypothesis #2/#3's test above scored raw booster probabilities with no calibration step at all.
- Model/calibrator version drift: is the exact model+calibrator pair actually deployed right now identical to `jra-running-style-lgbm-prod-v3`'s artifact used in this test?
- Measurement-window/population definition differences beyond the gap-date confound already found (e.g. tie-breaking, timing of when "served" predictions get locked in vs. when ground truth is captured).

**Post-campaign handoff:** inv-jra-rs returns 22:20 JST. Recommend resuming here with **live-serving-path actual reproduction** as the next concrete step — all three feature-divergence-family hypotheses (matview-fix-recovers-WF, raw-reproduces-served, row-coverage-explains-served) are now exhausted; further investigation should target the serving pipeline itself (calibration, artifact version, live R2/Iceberg fetch) rather than re-testing feature-value divergence.

## Related but smaller: FP has a time-based version of the same weakness (not a flagship)

**Checked:** does `finish_position_features_duckdb.py` (FP train+serve build) have the same clean train=matview/serve=raw split as RS? **No** — FP's `build_rec_select_sql` builds the entire historical lookback from `race_entry_corner_features` in **both** train (`--from-date`/`--to-date`) and serve (`--target-date`) modes. The only raw-source fallback (`resolve_upcoming_window`, active only in `--target-date` mode) is scoped to just the target race's own window, not to any of its historical inputs — so a horse's `recent_rank` is still built 100% from the matview either way.

**Partial mitigation already committed:** `2326bf1f` (2026-07-17 09:11 JST, "recover settled finish_position when corner-features row is stale") adds a tie-break so a target-window row with a stale-NULL matview `finish_position` gets its outcome recovered from raw `jvd_se`/`jvd_ra` — but the recovered row's own `corner_1_norm` etc. stay NULL (raw reads don't replicate the corner-normalization math), and again this only covers the target window, not history inputs.

**The real asymmetry is time, not code path:** training builds run against a date range that's usually had time to get backfilled (manual `win5-overlay` runs, the 07-17 heal, and now the twice-daily cron with 7-day lookback deployed 07-17). Serving depends most on a horse's most recent races — the least-healed part of the table at any given moment, since the reliable automated refresh has only existed since yesterday. This should shrink over time as the new cron self-heals, but training snapshots and live-serve snapshots of the same table will keep drifting apart for the most recent weeks until then.

**Disposition:** real, plausible, smaller-magnitude lever — not equal to the RS flagship (code path is genuinely different, and partial mitigation already exists). **Recommended as a post-campaign follow-up**, not part of this campaign's scope. If picked up, inv-jra-rs's methodology (correlate diverging predictions against gap-day exposure in recent history) transfers directly to measure FP's actual magnitude.

**Separately noted, different bug class, not chased:** `predict_upcoming.py`'s `_focused_full_prediction_complete` also reads `race_entry_corner_features` — for its "expected entrant count" completion check, not feature values. A gap-day there could under-report expected entrants (same root table, different symptom). Flagged for awareness only.
