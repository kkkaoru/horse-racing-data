## Requirements

- Application reads and domain writes use R2 Data Catalog, not Neon.
- Neon is a differential daily backup, outside the serving dependency graph.
- Additional user requirement: migrate vector storage/search dependencies to Cloudflare Vectorize. Preserve dimensions, distance metric, embedding model/version, identifiers and filter semantics; validate backfill and query parity before cutover.
- All D1 data must be migrated and queryable in Catalog, including operational state.
- Cache API and KV use explicit TTLs and write-aware invalidation; never describe local Cache API deletion or eventually consistent KV deletion as a global purge.
- Do not delete existing data or remove bindings until migration completeness and replacement behavior are verified.

## Findings

- `daily-keiba-sync`: Catalog-first Iceberg writes exist, but run completion and realtime discovery currently wait for Neon. D1 holds leases, cursors, position indexes and operation journals. Neon upserts rewrite unchanged records, and duplicate queue deliveries can rewrite a completed table.
- `pc-keiba-r2-catalog`: existing Cache API + KV serving; descriptor deletion uses `allSettled` and local deletion, not global invalidation.
- `pc-keiba-viewer`, `sync-realtime-data`, `sync-realtime-data-hot`: PostgreSQL/Hyperdrive runtime dependencies remain. D1 bindings also remain in features and cron workers.
- `finish-position-cron`: heavy source reads use Catalog, but readiness, prediction persistence and warmup paths still use Neon.
- `mlflow-ui-proxy`: source fingerprint uses Neon; this file already has unrelated working-tree changes and must not be overwritten.
- Many local/offline scripts still use PostgreSQL; distinguish local input from production Neon usage rather than deleting all PostgreSQL support.

## Implementation sequence

1. Reduce backup write amplification: conditional changed-row upserts and duplicate-delivery guards, with tests and full package verification.
2. Decouple realtime notification/serving readiness from Neon backup success, preserving durable recovery for notification and backup separately.
3. Inventory D1 tables and runtime SQL callers; define typed Catalog schemas, keys and mutation contracts. Preserve strong concurrency guarantees for leases/journals with a transactional coordination replacement rather than eventual KV caches.
4. Implement durable Catalog publication and resumable D1 export/backfill with checkpoints, count/key/hash reconciliation and deletion handling. Retain source until validation.
5. Switch each production reader/writer with regression tests, without fallback to Neon. Cover prediction and premium-data persistence as well as race data.
6. Implement revision-addressed Cache API/KV serving and durable invalidation/publication. TTLs must be workload-specific; old fills cannot revive old revisions after writes. Fetch/CDN cache is only applicable where requests actually traverse that cache, not automatically to service bindings or R2 bindings.
7. Verify types, lint and coverage for every changed package. Perform authorized production migration/cutover only after reconciliation; record deployment IDs, counts and Neon write metrics.

## Safety constraints

R2 Data Catalog is Iceberg, not a transactional drop-in D1 binding. Exporting D1 rows to plain R2 JSON is not a Catalog migration. Coordination data needs both queryable Catalog publication and correct serialized mutation semantics. Cache API is colo-local; KV is eventually consistent. TTL alone is not write consistency.
