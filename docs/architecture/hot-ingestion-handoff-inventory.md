## Gates before attaching callers or stopping source writes

1. **Queue outage handling:** guarded `-137` installed and verified the explicit source DLQ, and `-155` deployed tracked archival plus periodic observation while preserving policies. Configuration protection is established; genuine archival/destination delivery and observation-gap coverage are not yet established. Cloudflare documents a default of **3 retries**, permanent deletion on exhaustion without a DLQ, a maximum of **100 retries**, and retention configurable up to **14 days**. A DLQ without a consumer is not permanent storage (the DLQ guide describes four days); finite retention still deletes old messages. `ack()`/`retry()` obey **first call wins**, so an early ack cannot be reversed. Do not introduce a mandatory RPC dependency and assume failed acceptance retries forever. Preserve and recheck the verified retry/retention/dead-letter policy; establish recovery ownership and monitoring liveness before adding mandatory ordinary-input dependencies. Never acknowledge a message merely because its input was retained. Sources: [DLQ](https://developers.cloudflare.com/queues/configuration/dead-letter-queues/), [retries](https://developers.cloudflare.com/queues/configuration/batching-retries/), [limits](https://developers.cloudflare.com/queues/platform/limits/).
2. **Outcomes and replay:** the inbox deliberately lacks a completed/delivered state. Define durable outcomes, unknown-ack recovery, and idempotent target operations before replay. Replaying every accepted historical intent would repeat already successful work; a resolved outer handler is not proof that all sub-operations succeeded.
3. **Time-sensitive data:** retaining a `fetch-odds` intent does not preserve the odds observable at its original execution time. Replaying later reads different upstream data. Keep raw odds acquisition/publication operating through handoff, or establish a justified transition design that preserves those observations. An input journal alone does not prove zero data loss.
4. **Old handlers:** code review confirms `writeOddsPayloadToR2` currently reads/merges and unconditionally writes the live payload **before** snapshot/staging retention, with no ETag compare-and-set. Pipeline send errors are swallowed, while NDJSON staging is awaited. Snapshot keys use the supplied fetch timestamp, not a content digest. `fetchAndStoreOdds` captures that timestamp before scraping, completes D1 afterward, and its caller mirrors the returned scrape into KV/DO caches. Thus late publication can regress the live object/cache, and a job receipt alone cannot fix ordering or preserve all raw responses. D1 guards can reject late source DML, but do not fence stale R2/cache writes or prove old HTTP handlers drained. Reconcile ownership/version checks for domain publication as well as control state. Do not infer drain from 15-minute Queue/Cron limits.
5. **Scope and reconciliation:** cover Queue, Cron, recovery and authenticated HTTP writers, then verify complete live DDL/trigger ownership and create a fresh fenced generation. Existing v1 snapshots and a healthy service are insufficient cutover evidence.
6. **No destructive shortcuts:** no DELETE/DROP/TRUNCATE/retention of `fetch_logs` or `odds_fetch_state`; no legacy odds-snapshot writer revival, manufactured events or induced production failures.

A queue-only receipt pilot may provide limited observation evidence, but it must remain explicitly non-authoritative for the other paths and cannot unlock source fencing.
